# Supported PDF/X-4 output review

This document describes the library's generated structures and selected CMYK output mode. The [public references](public-technical-sources.md) describe the underlying PDF format. Current checks cover the supported API; the library is not a general PDF/X validator and its exhaustive coverage flag remains false.

## Generated-output checks

The custom output condition needs a human-readable output-intent `Info` description. An output-condition description is also useful. The destination ICC profile must remain embedded as its exact accepted bytes; its description tag alone does not establish the intended printing condition.

PDF/X requires a nonempty title. The writer must check the actual serialized size of individual content text strings, including UTF-16 encoding where used, as well as its aggregate input budget. Graphics-state limits include the automatic state save when a Form is invoked; checking each stream in isolation misses nested invocation paths. Output references must stay within the checked architectural object limit.

ICC container usability and accepted ICC specification editions are different checks. The existing fixture uses valid v2.2 encoding. Version screening must preserve that fixture and distinguish referenced v4 editions from arbitrary newer profiles. Header screening supplements confined parsing and transform probing; it does not establish complete ICC certification.

These checks form part of the implemented generation contract. Current verification receipts and [verification status](../verification-status.md) record which corrections and generated bytes have been checked.

The October 6 focused font/metadata repair applies PDF Reference 1.6 section
5.9.2: each ToUnicode destination contains at most 512 UTF-16BE bytes. Neutral
construction, retained compatibility mappings and shared resource emission
enforce that bound. Both ToUnicode emitters now write CMapType 2 directly, as
required by Adobe Technical Note 5099 section 1.3.1 and illustrated in PDF
Reference example 5.16. Identity-H Encoding CMaps are unchanged. CR character
references preserve decoded Info/XMP title equality under XML line-ending
normalization. New font-bearing PDFs differ from the earlier checked bytes;
earlier exact-byte checker results remain historical evidence.

PDF Reference implementation note 60 (printed pages 1014-1015) describes
width consistency with the embedded program. It does not select nearest-integer
rounding or specify a permitted numerical tolerance. A +1
difference from an audit using nearest rounding therefore does not by itself
establish nonconformance. The current worker floors the exact advance scaled to
1000 units; its nonnegative width error is less than one such unit. Nearest
rounding reduces that bound but still loses fractional precision. No worker
change is made solely to match that comparator, and this finding supplies no
blanket normative approval of width quantization. Independent CFF versus SFNT
metric agreement is a separate question.

## Supported structures

| Area | Supported-output contract |
| --- | --- |
| Page format | Emit PDF 1.6 and complete composed pages through the closed public content model. Diagnostic negative candidates have a separate development purpose. |
| Document presentation | No non-print annotation appearances or alternate visible representations are emitted. Metadata describes the document. |
| Resource embedding | Embed the resources needed for complete exchange; reject missing resource references. |
| Color profiles | Use one exact embedded CMYK printer profile. DeviceCMYK and DeviceGray content are permitted. Unmanaged RGB requires characterization or conversion before this print mode; it is supported separately in ordinary PDF. |
| Fonts | Embed exact prepared TrueType/CFF programs, CID mappings, widths and Unicode extraction information. Preserve the native composite-font architecture. |
| Names | Emit bounded, escaped PDF names and bounded prepared font names. |
| Self-contained resources | Generate self-contained resources without external stream files, OPI or reference XObjects. |
| Stream encoding | Use the supported Flate resource encoding and unfiltered metadata. Direct encoded-image insertion would require its own filter contract. |
| Trapping metadata | Report untrapped output consistently in metadata; no trapping network is emitted. |
| Descriptive metadata | Supply required descriptive metadata and identifiers with matching document-info values. Validate required title and dates. |
| Output identity | Identify only the selected embedded-profile PDF/X-4 mode. Ordinary output carries no PDF/X identity. |
| Page boxes | Validate ordered media, bleed and trim boxes. These rules do not create a universal minimum bleed or image resolution. |
| Graphics states | Use defined alpha, soft-mask and blend graphics states; do not emit transfer functions or halftone overrides. |
| PostScript objects | No PostScript XObjects are emitted. |
| Access restrictions | No encryption or access restriction dictionary is emitted. |
| Image variants | No alternate image arrays are emitted. |
| Annotations | No annotation inputs or output are provided by this generation API. |
| Actions | No action or script inputs are provided. |
| Content operators | Generate fixed PDF operators; there is no arbitrary operator injection API. |
| Transparency | Live transparency and PDF-defined blend modes are allowed. Print composition groups use CMYK; internal luminosity masks use Gray. Verify new gradient masks and group placement on actual output. |
| Viewer preferences | No viewer-preference overrides are emitted. |
| Alternate presentations | No alternate presentations are emitted. |
| Rendering intent | Preserve the default relative colorimetric rendering intent unless a future explicit contract adds another defined intent. |
| Layers | No optional-content layers are emitted. Adding layers would require a separate contract. |
| Output limits | Bound serialized strings, names, CIDs, object allocation and executed graphics-state depth. Keep input/memory admission separate from these format limits. |
| Forms | No XFA or AcroForm inputs are provided. |
| Encoded image input | No JPEG2000 stream is emitted; decoded images are re-encoded as supported pixel streams. |
| External profiles | External-profile PDF/X-4p is outside the supported embedded-profile mode. |

## Color and gradient implications

Native CMYK and gray gradients, live transparency and the standard blend modes are compatible with the selected print mode. They do not require whole-page rasterization or a commercial runtime. RGB ordinary documents have their own documented blending-space policy. An ordinary mixed-color document's group space determines how colors combine; it must not be described as preserving every CMYK component numerically through RGB composition.

Separate native color and alpha gradient functions interpolate the authored components independently. This is an explicit library convention and can differ from premultiplied web-gradient fades. Axial/radial shading, hard interior transitions and endpoint padding are covered by this release; future gradient families require their own contracts.
